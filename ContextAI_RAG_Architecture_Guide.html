1. Master Architecture Flowchart

Ingestion Flow: PDF Upload → pypdf Text Extraction → 4000-char Slicing (500 overlap) → all-mpnet-base-v2 768-dim Embeddings → SQLite Storage → FAISS IndexFlatL2 + In-Memory BM25 Index.

Query Flow: User Chat → Regex Pronoun Trigger → Gemini Query Reformulation → LangGraph query_node → Concurrent FAISS + BM25 Search (top 50 each) → Adaptive Weighted RRF → Cross-Encoder Reranker (ms-marco L-2) → Retrieval Distance Evaluation → Context Compression (top 12 sentences) → Grounded Generation (Gemini) → Citation Verifier Critic → Final Response.

2. Component Deep Dives (Code Grounded)

1. Document Loading & PDF Text Extraction
Ingestion
What & Why
Extracts raw human-readable string text from binary PDF streams. LLMs and vectorizers cannot process raw PDF bytecode, font tables, or compressed vector graphics.
Where in ContextAI
app/services/pdf_service.py → extract_text_from_pdf(file_path). Called in documents.py inside process_document_background().
Input → Output
Input: uploads/document.pdf (Binary file)
Output: extracted_text: str (Clean concatenated document string)
Trade-offs & Alternatives
Used: pypdf (Pure Python, zero OS dependencies).
Alternatives: PyMuPDF (fitz) for 15x faster extraction, pdfplumber for complex tables, OCR (Tesseract) for scanned images.
Interview Summary "For ingestion, we use pypdf in pdf_service.py to iterate over PDF pages and extract plain text. We chose it for its lightweight, pure-Python portability without requiring external C++ toolchains like Poppler."
2. Text Chunking
Preprocessing
What & Why
Splits long document strings into fixed passages with overlap. Solves model sequence token limits and enables precise, pinpointed vector search rather than retrieving whole multi-topic books.
Where in ContextAI
app/services/chunking_service.py → chunk_text(text, chunk_size=4000, overlap=500).
Input → Output
Input: Extracted document string (1.2M characters)
Output: chunks: list[str] (Array of 4000-character overlapping strings)
Trade-offs & Alternatives
Parameters: chunk_size=4000, overlap=500 (step=3500).
Trade-off: Sub-millisecond string slicing vs. potential mid-word cuts at boundaries.
Alternative: Recursive boundary chunking (splitting on \n\n, \n, sentence punctuation).
Interview Summary "We implemented sliding-window character chunking in chunking_service.py with a size of 4000 characters and 500 characters overlap (step=3500), guaranteeing deterministic boundary continuity across chunks in sub-millisecond execution time."
3. Dense Vector Embeddings
Embedding Model
What & Why
Transforms textual concepts into dense 768-dimensional float vectors where semantic similarity corresponds to geometric proximity.
Where in ContextAI
app/services/embedding_service.py → Model: SentenceTransformer("all-mpnet-base-v2").
Functions: generate_embedding() (query) & generate_embeddings() (batch size 32).
Input → Output
Input: String query or list of chunks
Output: 768-dimensional float vector (e.g. [-0.0245, 0.0812, ...])
Trade-offs & Alternatives
Used: all-mpnet-base-v2 (Top-tier local accuracy, zero API cost, local privacy).
Alternatives: OpenAI text-embedding-3 (cloud, costs API fees), all-MiniLM-L6-v2 (faster, 384-dim).
Interview Summary "We utilize local all-mpnet-base-v2 via sentence-transformers in embedding_service.py to generate 768-dim embeddings without external API costs or privacy risks, batching document chunks in sets of 32 for vectorized PyTorch encoding."
4. Vector Indexing & FAISS
Vector Storage
What & Why
High-performance C++ vector index that executes ultra-fast Euclidean (L2) distance nearest-neighbor lookups across high-dimensional vector spaces.
Where in ContextAI
app/services/vector_service.py → FAISSVectorStore using faiss.IndexFlatL2(768). Persisted to faiss_data/index.faiss and faiss_data/chunk_ids.json.
Input → Output
Input: 768-dim query vector, top_k=50
Output: list[tuple[chunk_id, distance]]
Trade-offs & Alternatives
Used: IndexFlatL2 (Exact search, 100% recall, zero training overhead, 0.4ms search latency).
Alternatives: Qdrant, Pinecone, Milvus, pgvector.
Interview Summary "We use FAISS (`IndexFlatL2`) in `vector_service.py` to index our 768-dim vectors. It executes exact L2 nearest-neighbor search in under 1 millisecond and maintains a parallel JSON ID mapping file to bridge FAISS integer positions with SQLite database records."
5. Sparse Lexical Search (BM25)
Lexical Search
What & Why
Probabilistic TF-IDF ranking algorithm that searches exact keywords, codes, mission numbers (e.g. 'Pioneer 0', 'Luna 1'), and acronyms that dense vectors miss.
Where in ContextAI
app/services/bm25_service.py → BM25Service using rank_bm25.BM25Okapi.
Input → Output
Input: Query string, top_k=50
Output: list[tuple[chunk_id, bm25_score]]
Trade-offs & Alternatives
Used: In-memory pure-Python BM25Okapi (zero external infrastructure).
Alternatives: Elasticsearch, SPLADE (neural sparse), SQLite FTS5.
Interview Summary "We maintain an in-memory BM25Okapi index in `bm25_service.py` to handle exact keyword lookups, mission designations, and acronyms, directly solving the vocabulary mismatch limitations of dense bi-encoders."
6. Conversational Query Reformulation
Query Transformation
What & Why
Detects multi-turn follow-up questions containing pronouns ('it', 'its', 'they') and rewrites them into standalone search queries using past conversation context.
Where in ContextAI
app/services/query_reformulation_service.py → reformulate_query() with 13 compiled regex patterns in is_follow_up_question().
Input → Output
Input: "What were its scientific instruments?" + History
Output: "What were the scientific instruments on Pioneer 0?"
Trade-offs & Alternatives
Used: Regex guard + gemini-3.5-flash-lite (Zero latency on direct questions, LLM precision on follow-ups).
Alternative: Always-on LLM rewriter (adds 500ms on every user query).
Interview Summary "In `query_reformulation_service.py`, we implement regex-gated query rewriting. When pronouns like 'it' or 'they' are detected, `gemini-3.5-flash-lite` resolves the conversational antecedent before searching, bypassing the LLM call for direct queries."
7. Query Intent Analysis Agent
Agentic Routing
What & Why
Inspects structural and lexical indicators to adaptively assign retrieval strategies (semantic / keyword / broad) and adjust candidate pool sizes (3 vs. 10).
Where in ContextAI
app/services/agents/query_agent.py → analyze_query(). Forms the first node (query_node) in rag_graph.py.
Input → Output
Input: "List all probes sent to Venus"
Output: {'is_broad': True, 'retrieval_count': 10, 'retrieval_strategy': 'broad'}
Trade-offs & Alternatives
Used: Fast deterministic rule classifier (0ms latency, zero token cost).
Alternative: LLM Function Calling / Semantic router (slower, non-deterministic).
Interview Summary "Our `query_agent.py` analyzes query intent at 0ms cost. It classifies the search into semantic, keyword, or broad categories, dynamically scaling `retrieval_count` between 3 and 10 and setting adaptive fusion weights."
8 & 9. Concurrent Hybrid Retrieval & Weighted RRF
Hybrid Fusion
What & Why
Executes FAISS and BM25 concurrently using ThreadPoolExecutor(2) and combines their non-calibrated scores using Reciprocal Rank Fusion ($k=10$).
Where in ContextAI
app/services/agents/retrieval_agent.py → retrieve_documents() & weighted_reciprocal_rank_fusion().
Formula in Code
Score(d) = Σ [weight / (10 + rank)]
Adaptive weights: Semantic (1.5 / 0.5), Keyword (0.5 / 1.5), Broad (1.0 / 1.0).
Performance Impact
Latency: 0.0032s (3.2ms)
Recall Gain: +6.12% to +10.00% recall boost over FAISS alone.
Interview Summary "In `retrieval_agent.py`, we run FAISS and BM25 concurrently on 2 worker threads, merging top 50 candidates using Weighted Reciprocal Rank Fusion ($k=10$). RRF is scale-invariant and delivered a measured +6.12% recall gain over dense search."
10. Cross-Encoder Reranking
Second-Stage Reranker
What & Why
Performs deep multi-layer bidirectional cross-attention across (Query, Chunk) token pairs to eliminate false positive candidates from bi-encoder retrieval.
Where in ContextAI
app/services/reranker_service.py → RerankerService using cross-encoder/ms-marco-MiniLM-L-2-v2.
Benchmark Results
Recall@5: 84.00% (42/50 hits)
Relative Gain: +24.00 pp over FAISS baseline (+18.00 pp over Hybrid).
Trade-offs
Latency: ~2.12s on CPU.
Trade-off: Adds CPU compute time in exchange for highest precision in the architecture.
Interview Summary "We use `cross-encoder/ms-marco-MiniLM-L-2-v2` in `reranker_service.py` for second-stage reranking over top 50 hybrid candidates. In our benchmarks across 50 questions, this lifted Recall@5 from 60.00% to 84.00%."
11. LangGraph State Machine & Adaptive Fallbacks
Agentic Orchestration
What & Why
A cyclic state machine that evaluates retrieval confidence in flight and triggers broad fallback retries if vector distance thresholds exceed limits (> 0.8).
Where in ContextAI
app/services/agents/rag_graph.py → build_rag_graph() with RAGState TypedDict.
Graph Routing Logic
retrieve → retrieval_router (checks is_retrieval_weak) → retry_retrieval (widens count to 10) → generate.
Advantage over Linear Chains
Recovers gracefully from retrieval misses without generating hallucinations.
Interview Summary "Our LangGraph workflow in `rag_graph.py` replaces rigid linear RAG chains. It checks whether the average FAISS distance exceeds 0.8. If retrieval is weak, it dynamically routes to a retry node to widen retrieval before generation."
12. Context Compression
Extractive Filter
What & Why
Splits retrieved chunks into sentences and filters for the top 12 (or 30) most query-relevant sentences using token set intersection.
Where in ContextAI
app/services/context_compression_service.py → compress_context(max_sentences=12).
Input → Output
Input: 4000-char context (~40 sentences)
Output: 1200-char context (12 highest-scoring sentences preserved in original document order)
Why It Matters
Solves the 'Lost in the Middle' problem, reduces prompt fluff, and saves input tokens at 0.5ms execution time.
Interview Summary "In `context_compression_service.py`, we extractively filter the top 12 sentences based on query keyword overlap while preserving their chronological document order, maximizing prompt density and lowering LLM input token load."
13 & 14. Answer Generation & Citation Verification
Generation & Critic
Generation (response_agent.py)
Uses gemini-3.5-flash-lite with strict grounding prompt: 'Answer using ONLY provided context. If absent, say: I couldn't find that information.'
Verification (citation_verifier.py)
A secondary LLM critic node that performs an entailment check (returns YES or NO).
Self-Correction Loop
If verification fails (NO), LangGraph routes to regenerate_node once. If it fails a second time, routes to safe_response_node.
Advantage
Enterprise-grade hallucination prevention via Generate-then-Verify loop.
Interview Summary "We synthesize grounded answers using `gemini-3.5-flash-lite` in `response_agent.py` and validate claims with an independent citation verifier critic in `citation_verifier.py`. If unverified claims appear, LangGraph executes an automated regeneration loop."

5. ContextAI Interview Cheat Sheet

1. Ingestion: pypdf + character sliding window (4000/500) → all-mpnet-base-v2 768-dim embeddings in SQLite + FAISS (IndexFlatL2) and in-memory BM25Okapi.
2. Retrieval: Parallel FAISS + BM25 via ThreadPoolExecutor fused with Weighted RRF ($k=10$).
3. Accuracy vs. Speed: Fast Mode (Hybrid RRF, 66% recall at 10.7ms) vs. Accurate Mode (Cross-Encoder ms-marco-MiniLM-L-2-v2, 84.00% Recall@5 at 2.12s).
4. Orchestration: LangGraph state graph evaluates average vector distance (> 0.8) for retry and runs an extractive sentence filter (top 12).
5. Generation & Safety: gemini-3.5-flash-lite synthesizes answers and an independent critic verifies factual entailment before returning.
6. Evaluation: 50-question human-verified ground-truth evaluation benchmark runner.
